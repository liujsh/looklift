# LookLift Agent Native 面试审视

> 用途：以 Agent 岗位面试官视角审视项目含金量，区分已实现事实、可辩护亮点与后续补强方向。
> 本文不是已实现架构实况；正式产品契约见 `product/requirements.md` 与 `versions/v2.6/`。

## 一句话判断

LookLift 目前更准确是 **AI-first 的垂直修图应用，具备受控 agentic editing loop**，已经超过“聊天框套模型”；
但 v2.1 的核心仍是单次 `chat_step` 生成结构化参数建议，v2.5 是确定性批处理，还不足以证明统一 Harness、
工具循环、Skill 生命周期和领域 Agent 评测。简历项目名可以使用“受控白盒 AI 修图 Agent”，面试时应主动说明
Runtime 仍在建设，不能把批处理或 Skill 文档包装成自主智能体。

“白盒”本身不是 Agent 智能水平。它的 Agent 价值在于定义了可枚举动作空间、可观察环境状态、可验证终态与
副作用边界；Agent 好坏仍要由规划、工具选择、反馈利用、停止策略、恢复和领域评测证明。

## 当前真正有价值的亮点

1. **领域动作是白盒的**：模型不能直接写像素，只能修改参数契约允许的全局调色参数；用户、模型、模板和
   自动化最终共享同一份 `analysis`。
2. **动作结果进入真实环境**：候选参数会经过本地渲染，画布、直方图、裁切提示和 before/after 提供可观察结果，
   不是只返回一段文字。
3. **副作用边界清楚**：AI 候选默认只存在于临时预览，用户确认后才进入正式版本；取消、晚到响应和失败不会
   静默移动正式状态。
4. **有工程化安全边界**：外部模型只接收 2048px 无 EXIF 代理图，参数路径、范围、曲线和输出路径均由本地校验。
5. **有可恢复执行地基**：v2.5 已具备冻结计划、逐项状态、协作式取消、进程中断恢复和失败重试，适合承接未来
   Agent 的长任务执行。
6. **不是纯 LLM 项目**：Python 图像引擎、Tauri 桌面端、版本存储、多供应商和离线测试形成完整产品闭环。

## 面试官会重点拷打什么

| 追问 | 当前诚实回答 | 需要补的证据 |
|---|---|---|
| 为什么叫 Agent，不是一次 Function Calling？ | 目前只有受控建议、真实预览和按需精修，统一 Harness 与工具循环仍在下一阶段 | 多步工具轨迹、真实反馈利用和停止原因 |
| Agent 自己决定过什么？ | 决定参数操作与解释；是否继续精修、是否提交由用户控制 | 在预算内选择工具、模板、诊断步骤与候选修正 |
| 模型看到了执行结果吗？ | 精修时可看当前代理图，但缺少统一的结构化观察协议 | 渲染后指标、参数差异和失败结果回灌 Agent |
| 为什么只有一个主要 Tool 也叫 Agent？ | Agent 性不来自 Tool 数量，而来自是否根据真实候选反馈继续决策 | 证明 `render_candidate` 结果回灌后改变后续参数或终态 |
| 如何防幻觉和越权？ | 参数白名单、本地范围校验、安全代理、候选不直接提交 | 工具级策略门、预算、路径能力句柄和越权轨迹测试 |
| 如何评估 Agent，而不是只测代码？ | 主要是模块测试与 mock provider 测试 | 场景集、轨迹断言、任务成功率、安全违规率和冗余调用 |
| Memory 是什么？为什么需要？ | 正式消息与版本持久化，不保存未确认候选 | 可恢复 Agent Run；长期偏好只保存用户明确确认的事实 |
| 失败后如何恢复？ | 自动化任务可恢复，聊天候选以正式版本为边界 | Agent Run 从最后正式版本和已完成工具事件恢复 |
| 成本和延迟怎么控制？ | provider 有超时，精修轮数有限 | 每次运行的模型/渲染预算、耗时与停止原因统计 |
| 为什么不用 LangGraph/多智能体？ | 通用 Loop 优先委托成熟 CLI/Harness，LookLift 专注领域能力、策略和评测 | 证明双 Harness 语义一致且不把外部 CLI 权限带进照片域 |
| CLI 和裸模型 API 如何同时支持？ | 当前 CLI 只被当作模型调用后端，两条路径还没有统一 Agent ABI | 外部 CLI Harness 与内嵌 Harness 归一到同一事件、工具、取消和恢复契约 |
| Skill 为什么不是 Prompt 文件？ | 当前 Skill 尚未接入运行时 | 触发条件、所需观察、允许能力、风险、完成 rubric、加载轨迹与对照评测 |
| 图片里的文字会不会提示注入？ | 不能靠 prompt 完全解决，但本地工具白名单限制后果 | 将图片文字视为不可信内容，加入越权诱导场景测试 |
| 比 Lightroom/Photoshop AI 强在哪？ | 不声称能力更全；优势是参数全白盒、可学习、可导出和本地可控 | 用真实任务展示“建议—预览—解释—手调—导出”证据 |

## 面试回答主线

不要从“我接了几个模型”开始。推荐按以下顺序回答：

1. 修图 Agent 最大风险不是模型不会聊天，而是它可能不可解释地破坏作品，所以先建立白盒参数 ABI 和临时版本边界。
2. 模型只负责高层决策，所有动作必须经过本地工具、参数契约和真实渲染；永久提交、导出和批量执行由策略门控制。
3. v2.1 先验证单轮建议与人在回路，v2.5 补可恢复长任务；v2.6 通过 Harness Gateway 将外部 CLI 与内嵌模型循环
   统一为可观察、可评估的领域 Runtime，避免重复发明通用 Agent 基建。
4. 不用多智能体制造复杂度，先用单 Agent + 确定性工具完成可测闭环；只有出现明确的并行专业角色需求才拆分。

## 改进优先级

### P0：让 Agent 名称站得住

- 建立薄 Domain Runtime；本地 CLI 负责原生 Agent Loop，API 内嵌 Harness 通过同一 Domain Pack 和 Tool 语义接入。
- 将机器动作收敛为高信息密度的 `render_candidate`，自动返回参数差异、真实候选图和可靠指标。
- 建立持久化 Agent Run，记录目标、简要计划、工具调用、观察结果、策略裁决、预算和停止原因。
- 将 `chat_step` 降为兼容/快速路径，由 Runtime 统一多步运行语义；候选仍需用户确认，不扩大副作用。
- 在 UI 展示可理解的执行轨迹，但不暴露或依赖模型隐藏思维链。

### P1：让效果可以被证明

- 建立离线场景评测集，覆盖曝光修复、色偏、模板自适应、能力不足、取消、工具失败和越权诱导。
- 同时评估任务结果与过程：参数方向、裁切变化、工具选择、调用次数、停止原因和正式版本是否被污染。
- 真实 provider 与主观观感进入人工评测，不进入默认 CI，不把模型随机性伪装成确定性单测。

### P2：让 Skill、自动化和插件形成体系

- AgentSkill 是带适用范围、诊断、条件策略、复核、停止和 rubric 的领域 SOP；Tool 执行机器动作；Workflow 固化
  可重复步骤；Template 是可执行参数案例；Plugin 负责受控分发。
- 首批 Skill 接入运行时后，必须能影响计划或验收标准，并在轨迹中说明加载原因；不能只是仓库里多了 Markdown。
- 插件应建立在稳定 Capability 与权限模型之上，因此排在 Agent Runtime 之后。
