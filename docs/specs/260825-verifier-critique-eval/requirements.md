# 需求文档

## 简介

建立独立的 Verifier、Critique 与离线评测层，将契约、安全、领域和渲染质量检查从 Candidate Runtime 中分离，并为真实模型与人工评测预留统一报告格式。

## 需求

### 需求 1 - 分层验证

**用户故事：** 作为工程师，我想要在候选进入用户界面前执行分层验证，以便错误不会污染正式版本。

#### 验收标准

1. 当候选产生时，系统应该依次执行 Contract、Domain 和 Render Verifier，并返回结构化结果。
2. 当任一硬门禁失败时，系统应该拒绝候选并保留失败分类、证据和输入摘要。

### 需求 2 - 领域 Critique

**用户故事：** 作为摄影师，我想要看到与 Skill 目标相关的批评意见，以便决定是否接受候选。

#### 验收标准

1. 当 Skill 声明 Critique policy 时，系统应该检查其适用条件、禁用条件和能力不足条件。
2. Critique 只能提供解释和建议，不得直接修改正式参数。

### 需求 3 - 可重复离线评测

**用户故事：** 作为维护者，我想要不依赖真实 Provider 运行评测，以便稳定比较版本和消融配置。

#### 验收标准

1. 当运行固定 Eval Case 时，系统应该输出终态、候选数、工具调用数、错误码、取消/晚到状态和版本不变量。
2. 离线断言不得把模型文字质量或主观审美冒充为硬指标。

### 需求 4 - 评测分层与报告

**用户故事：** 作为产品负责人，我想要区分自动化证据、真实模型结果和人工盲测，以便诚实判断发布门禁。

#### 验收标准

1. 报告应该分别标记 Contract、Fake Harness、Real Model Ablation 和 Human Pairwise 阶段。
2. 缺少真实照片或人工结果时，系统应该标记“待人工完成”，不得生成通过结论。

### 需求 5 - 用户复核门

**用户故事：** 作为用户，我想要在最终接受前复核候选和指标，以便保留对正式版本的控制。

#### 验收标准

1. 当候选通过自动验证时，系统应该进入 User Review Gate，而不是自动提交正式版本。
2. 当用户拒绝或取消时，系统应该保持正式版本和原图路径不变。
