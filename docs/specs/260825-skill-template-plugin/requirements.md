# 需求文档

## 简介

建立 Skill、Template 与受控 Plugin 的统一协议，使垂域知识、可复用参数方案和扩展能力能够组合、版本化、审计，同时不突破白盒参数与用户确认边界。

## 需求

### 需求 1 - 统一扩展描述

**用户故事：** 作为平台维护者，我想要用统一清单描述 Skill、Template 和 Plugin，以便目录、安装器和运行时可以一致校验。

#### 验收标准

1. 当加载扩展清单时，如果缺少 `specVersion`、稳定名称或版本，那么系统应该拒绝加载并返回结构化错误。
2. 当清单声明任务类型、输入和能力时，系统应该校验字段枚举、版本格式和能力白名单。

### 需求 2 - 多来源 Skill 合并与冻结

**用户故事：** 作为用户，我想要组合内置、用户、项目和插件 Skill，以便在不同项目复用垂域工作流。

#### 验收标准

1. 当多个来源提供同名 Skill 时，系统应该按明确优先级选择，并记录来源与 SHA-256。
2. 当一次运行开始时，系统应该把解析后的 Skill 复制到项目私有 staging 目录并冻结版本；运行期间源文件变化不得影响本次运行。

### 需求 3 - Template 与 Skill 分离

**用户故事：** 作为摄影师，我想要独立选择参数模板和诊断 Skill，以便更换工作流而不隐式改变参数方案。

#### 验收标准

1. 当模板声明兼容 Skill 时，如果当前 Skill 不匹配或禁用条件成立，那么系统应该阻止应用并说明原因。
2. 当模板被应用时，系统应该只允许白盒 `delta/set` 标量 Patch，不得包含曲线、Prompt、路径或脚本。

### 需求 4 - 最小权限 Plugin

**用户故事：** 作为用户，我想要安装社区扩展，以便增加连接器或垂域能力，同时控制其可访问的数据和操作。

#### 验收标准

1. 当插件请求能力时，系统应该要求用户授予最小能力集合，并在运行前展示数据范围与接收方。
2. 当插件尝试任意 Shell、Python、原图路径访问或黑盒像素修改时，系统应该拒绝调用并记录审计事件。

### 需求 5 - 生命周期与注册表

**用户故事：** 作为维护者，我想要安全安装、升级和卸载扩展，以便保留历史运行的可重现性。

#### 验收标准

1. 当安装或升级扩展时，系统应该验证签名/摘要、依赖和兼容版本，并保留旧版本。
2. 当卸载扩展时，如果已有运行引用该版本，系统应该保留其 staging 副本，不影响历史回放。
