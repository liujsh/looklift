# 需求文档

## 简介

本规格定义 LookLift 的 Agent 自动记忆与混合相关度召回能力。系统整体借鉴 OpenDesign：由 Agent/LLM/Connector 自动提炼并整理长期记忆，默认无需用户逐条确认；同时保留可查看、可撤销、可删除和可关闭的用户控制。召回不采用全量注入，而采用分层、作用域过滤、BM25 与向量检索融合、预算裁剪和运行快照。

## 用户故事

### 需求 1 - Agent 自动写入

作为用户，我希望 Agent 能自动记住稳定偏好和工作习惯，而不要求我每次点击确认。

验收标准：

1. 当 Agent、LLM 或 Connector 提炼出满足持久性、未来效用和隐私约束的候选时，系统应该经 Memory Gate 审核后直接写入并激活正式 Memory，并标记来源、置信度和证据。
2. 当候选只描述本次操作或临时状态时，系统应该将其限定为 `run` 作用域或丢弃，不得自动写入全局 Memory。
3. 当候选包含密钥、原图路径、EXIF 或其他禁止的敏感信息时，系统应该拒绝写入或完成脱敏后再写入。
4. 当自动写入完成后，用户应该能够通过设置页或自然语言指令查看、编辑、停用、删除和撤销该条目；自动写入不要求逐条确认。

### 需求 2 - 记忆分层与作用域

作为用户，我希望全局偏好、项目上下文和单次要求互不污染。

验收标准：

1. 当条目属于稳定用户背景时，系统应该保存为 `global`/`profile` 或 `fact`。
2. 当条目只适用于明确的 `project_id` 时，系统应该保存为 `project` 作用域并强制记录 `project_id`，没有匹配项目时不得召回。
3. 当条目只适用于当前运行时，系统应该保存为 `run` 作用域并强制记录 `run_id` 与过期策略，运行结束后不得进入长期召回。
4. 当不同作用域的条目冲突时，系统应该按 `run > project > global` 处理，并记录冲突原因。

### 需求 3 - 混合相关度召回

作为用户，我希望 Agent 只看到与当前修图任务相关的记忆，从而降低上下文长度和调用成本。

验收标准：

1. 当生成 Run 上下文时，系统应该从当前目标、图片分析、编辑参数、项目上下文和最近反馈构造 Recall Query。
2. 当普通 Memory 需要召回时，系统应该同时支持 BM25 稀疏检索和 embedding 向量检索，并使用稳定的排名融合算法合并结果。
3. 当条目属于 `profile` 时，系统应该在小型固定预算内优先注入，而不是因 query 未命中而完全丢失。
4. 当条目属于已启用且适用范围内的 `rule` 时，系统应该按规则作用域和产物类型加载，并不得因普通语义 Top-K 静默漏掉必需规则。
5. 当召回结果超过 Memory token 预算时，系统应该按优先级裁剪，并记录每条省略的原因。

### 需求 4 - 可解释上下文快照

作为用户，我希望知道本次运行使用了哪些记忆、为什么使用，以及哪些被省略。

验收标准：

1. 当 Domain Pack 编译完成时，系统应该记录 `used_memory_ids`、`used_rule_ids`、排名来源、版本和内容 Hash。
2. 当条目因相关度不足、预算不足、作用域不匹配、过期或冲突而未注入时，系统应该记录结构化省略原因。
3. 当 Run 开始后 Memory 被修改或删除时，系统应该保持本次已冻结快照不变。

### 需求 5 - 规则与反馈闭环

作为用户，我希望反复的修图纠正能沉淀为偏好，并在生成后检查当前 active 规则。

验收标准：

1. 当同类修图反馈跨多个 Run 重复出现时，系统应该聚合为候选偏好或规则，而不是依据单次操作改变全局偏好。
2. 当生成结果完成且存在适用规则时，系统应该执行规则自验证并记录 `pass`、`fail`、`fixed` 或 `skipped`。
3. 当自动记忆提取失败、无 provider 或被策略跳过时，系统应该记录状态和原因，不得阻塞主任务。

### 需求 6 - 配置与隐私控制

作为用户，我希望控制自动记忆和召回的范围。

验收标准：

1. 当用户关闭 Memory 总开关时，系统应该停止召回，但不删除已保存条目。
2. 当用户关闭自动提取时，系统应该停止聊天和行为事件的自动写入。
3. 当用户对当前 Run 禁用 Memory 时，系统应该只使用本次显式输入，不注入长期条目。
4. 当内容发送到外部模型或 Harness 时，系统应该只发送必要的脱敏 Memory 文本。

### 需求 7 - 记忆质量评测

作为开发者，我希望用可重复的离线数据和线上指标评估自动写入与混合召回，确保降低 token 成本不会损害修图质量。

验收标准：

1. 当运行离线评测时，系统应该分别报告自动写入 Precision/Recall、作用域准确率、泛化错误率、召回 Recall@K/Precision@K、规则覆盖率、噪声率、Token 成本和检索延迟。
2. 当比较全量、纯 BM25、纯向量和 Hybrid 方案时，系统应该使用同一组固定案例、同一模型和同一预算，并输出可复现的对比结果。
3. 当评测自动写入安全性时，系统应该覆盖临时状态、跨项目污染、冲突偏好、敏感信息和错误记忆撤销场景。
4. 当评测端到端修图收益时，系统应该比较无 Memory、全量 Memory 与 Hybrid Memory 的首轮接受率、重复纠正次数和错误干扰率。
5. 当 Hybrid 方案节省上下文但导致关键记忆召回或规则覆盖下降时，系统应该判定评测不通过，不得仅以 token 节省作为上线依据。

### 需求 8 - 记忆状态与生命周期

作为系统，我希望自动写入、停用、删除和撤销具有单一且可重放的状态语义。

验收标准：

1. 当条目被创建或更新时，系统应该使用 `state=active|disabled|deleted` 表示是否参与新 Run，不得使用 `confirmed` 作为激活条件。
2. 当条目作用域为 `project` 时，`project_id` 应该非空；当作用域为 `run` 时，`run_id` 和 `expires_at` 应该非空。
3. 当 Run 结束或过期时，系统应该从长期召回集合排除 run 条目，并保留事件和已冻结快照。
4. 当用户执行撤销时，系统应该按写入事件或条目版本幂等回滚，并使后续索引和新 Run 不再使用被撤销内容。
