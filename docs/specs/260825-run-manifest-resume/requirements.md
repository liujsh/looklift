# 需求文档

## 简介

建立 Run Manifest 与 Session Resume 机制，使 API/CLI 双 Harness 的运行可审计、可恢复，并在崩溃、重启或正式基线变化时保持安全。

## 需求

### 需求 1 - 运行事实清单

**用户故事：** 作为用户，我想要每次运行都有完整清单，以便复盘使用的模型、Skill、模板和候选变化。

#### 验收标准

1. 当运行创建时，系统应该记录照片与正式基线 Hash、Domain Pack、规则/记忆快照、Skill/Template、Harness、Provider、Model 和 Attempt。
2. 当工具调用或候选产生时，系统应该追加不可变事实、Revision、停止原因和用户确认结果。

### 需求 2 - 启动收敛与恢复

**用户故事：** 作为用户，我想要应用重启后看到中断状态，以便决定是否继续，而不是重复收费。

#### 验收标准

1. 当应用启动时，`starting/running/cancelling` 应该收敛为 `interrupted`。
2. 系统不得自动恢复模型调用；继续运行必须创建新的 Attempt。

### 需求 3 - 正式基线与过期

**用户故事：** 作为用户，我想要基线变化被识别，以便旧候选不会覆盖新编辑。

#### 验收标准

1. 当正式参数或照片 Hash 与 Manifest 不一致时，系统应该将运行标记为 `stale` 并禁止直接应用候选。
2. 候选恢复只能进入预览，不得自动进入正式版本。

### 需求 4 - API/CLI 切换

**用户故事：** 作为维护者，我想要在不同 Harness 间切换并保留统一事实，以便 Provider 差异不改变产品语义。

#### 验收标准

1. 当从 API 切换到 CLI 或反向切换时，系统应该保留规范化事件、候选和错误分类。
2. CLI 原生 Resume handle 只能作为优化信息，不能替代 LookLift Manifest 状态。

### 需求 5 - 离线恢复验证

**用户故事：** 作为工程师，我想要用确定性脚本测试恢复，以便不依赖真实模型验证安全性。

#### 验收标准

1. 当 Fake Harness 模拟崩溃、取消或晚到时，系统应该恢复最后一致事实并隔离晚到结果。
2. 测试应该断言正式版本、候选版本和隐私边界保持不变。
