# 需求文档

## 简介

完善“模型与提供商”设置和对话框模型选择，使用户能够在本机 CLI 与 API 两种入口之间进行可见、可控的选择，并跑通从选择到 CLI/API 调用的闭环。CLI 只管理本机已安装入口及其已发现模型；API 只管理已保存的配置。所有调用继续经过现有 Runtime、权限、候选校验与正式版本边界。

## 范围与非目标

- 范围：CLI 扫描、启停、状态与模型浏览、默认 CLI/模型；API 配置列表与编辑；对话框入口图标和模型选择器；设置页左侧导航收敛。
- 非目标：在设置页新增模型、CLI 诊断、自动安装 CLI、真实 Adobe Lightroom 操作，以及黑盒像素生成。
- 兼容：复用 `260826-runtime-harness-provider` 的 Runtime Registry、ProviderConfigStore、检测和安全契约，不建立第二套 Provider 真相源。

## 用户故事与验收标准

### 需求 1 - CLI 管理

**用户故事：** 作为用户，我想扫描和管理本机可用 CLI，以便知道哪些入口能用并选择默认模型。

1. 当用户进入“模型与提供商”页的 CLI 模式时，系统应该扫描并展示当前支持的本机 CLI；每项显示名称、可用/不可用、版本（若有）、模型数量和支持等级。
2. 当用户点击“重新扫描”时，系统应该重新探测可执行文件、认证状态和模型列表，并以新结果替换旧快照；探测失败应显示可操作的中文原因。
3. 当用户切换某个 CLI 的启用开关时，系统应该持久化启用状态；停用入口不得出现在对话框的可选入口列表中，也不得被自动调用。
4. 当用户点击 CLI 条目时，系统应该弹出模型列表；用户可以选择该 CLI 作为默认 CLI，并从其已发现模型中选择默认模型。
5. 当 CLI 未安装、未认证或无模型时，系统应该保留条目并明确状态，不显示为可用；页面不得提供“添加模型”或“诊断”操作。

### 需求 2 - API 配置管理

**用户故事：** 作为用户，我想查看和编辑已经保存的 API 模型配置，以便在不离开设置页的情况下切换调用入口。

1. 当用户进入 API 模式时，系统应该展示当前保存的 API 配置摘要（Provider、Base URL、模型、凭据是否已保存、可用状态）。
2. 当用户点击配置条目时，系统应该打开编辑弹窗；弹窗可编辑已有字段并保存或取消，取消不得改变已生效配置。
3. 当用户保存配置时，系统应该复用现有安全校验和凭据存储；前端和普通日志不得回显完整 API Key，保存失败不得标记为可用。
4. 当没有保存配置时，系统应该展示空状态和进入配置的操作；不要求在列表中直接创建多个模型配置。

### 需求 3 - 对话框模型选择

**用户故事：** 作为用户，我想在发送消息前快速确认当前使用的 CLI/API 和模型，以便避免误调用。

1. 当对话框加载且存在已选入口时，加号右侧应该显示当前 CLI 或 API 的图标、名称和模型摘要。
2. 当用户点击入口选择器时，系统应该弹出当前已启用且可用的 CLI 与已保存 API 配置；每个入口显示模型数量或错误状态。
3. 当用户选择 CLI 时，系统应该在二级列表展示其已发现模型；选择模型后应更新当前会话的运行时与模型，不影响其他会话。
4. 当用户选择 API 配置时，系统应该展示该配置可用模型（若 Provider 未返回列表则展示已保存模型），选择后更新当前会话；不可用入口不可提交调用。
5. 当用户未选择模型或入口不可用时，发送操作应该被阻止并给出中文提示，不得静默回退到其他入口。

### 需求 4 - CLI/API 调用闭环

**用户故事：** 作为用户，我想确认选择的 CLI/API 真的能执行修图请求，并且结果仍受白盒安全边界保护。

1. 当用户从对话框选择 CLI 或 API 并发送请求时，系统应该使用所选 Runtime ID 与模型创建并启动一次运行，调用链可被运行详情追踪。
2. 当调用成功产生候选时，系统应该继续进入现有候选渲染、Verifier 和用户确认流程；适配层不得直接修改正式版本。
3. 当调用失败、超时、取消或入口在发送前变为不可用时，系统应该显示分类错误并保持正式版本不变，不得自动切换入口。
4. 当测试 CLI/API 调用时，离线测试不得触网或调用真实模型；真实 CLI/API 只作为人工验收门禁。

### 需求 5 - 设置导航

**用户故事：** 作为用户，我想在设置页通过清晰的左侧导航访问已有设置，不被未实现功能干扰。

1. 当用户打开设置页时，左侧应该提供“回到首页”和已实现的“模型与提供商”“通用与隐私”“指令与记忆”入口，并标识当前项。
2. 当用户切换导航项时，系统应该只渲染对应现有页面并保留未提交草稿；不存在实现的媒体生成、OpenDesign MCP、隐私详情或关于页不得加入导航。
3. 当窗口窄于桌面布局时，导航应该按现有响应式约定重排为可操作的顶部/横向导航，不遮挡设置内容。

## 完成条件

- 三份规格通过一次一致性检查，接口边界与现有 Runtime/Provider 契约无矛盾即停止文档精化。
- 实施后需通过受影响前端测试、TypeScript 检查、Python 离线契约测试，并完成一次 CLI/API 人工调用验收。

## 交互补充（参考 OpenDesign）

### 需求 6 - 顶层运行模式切换

**用户故事：** 作为用户，我希望点击“本机 CLI”或“API 提供商”就立即切换当前运行模式，以便不再区分隐藏的实验性设置状态。

1. 当用户点击“本机 CLI”分段项时，系统应该立即将当前会话的执行模式切换为 CLI，并展示 CLI 入口清单；点击“API 提供商”时同理切换为 API 模式。
2. 当模式切换发生时，系统应该保留两种模式各自的草稿、默认入口和模型；切换不得自动发送请求或覆盖另一模式配置。
3. 当当前模式没有可用入口时，系统应该展示空状态和“前往设置”操作，不得静默回退到另一模式。

### 需求 7 - 输入框入口与设置跳转

**用户故事：** 作为用户，我希望在输入框附近看到当前模式和模型，并能快速打开对应设置。

1. 当对话框加载时，输入框加号右侧应该显示当前 CLI 或 API 提供商图标、名称和模型；未完成配置时显示“未配置”。
2. 当用户点击该入口时，系统应该弹出当前模式的模型选择器：CLI 模式展示当前可用 CLI 及其模型，API 模式展示当前 API 提供商及模型。
3. 当模型选择弹窗打开时，底部应该提供“设置”按钮；点击后跳转设置页的“模型与提供商”分区，并关闭弹窗。
4. 当用户在弹窗中选择模型时，系统应该只更新当前会话的运行选择；后续请求携带冻结的 `execution_mode + runtime_id/provider_id + model`。

### 需求 8 - BYOK API Loop 兼容与 LookLift 约束

**用户故事：** 作为用户，我希望没有 CLI 时仍能使用 API Key 完成多轮修图，同时结果不会绕过 LookLift 白盒边界。

1. 当 API 模式运行且没有本地 CLI 时，系统应该通过本地 Daemon 代理向 Provider 发起 SSE/JSON 流请求，不得启动或隐式安装 Pi、OpenCode 等 CLI。
2. 当 Provider 返回工具调用时，系统应该执行受限工具循环并设置最大轮数；未知工具、非法参数、越界参数或未授权路径必须拒绝。
3. 当历史消息、工具结果或代理上下文接近预算时，系统应该先按优先级压缩/摘要，再按单条上限截断；截断必须产生结构化警告并保留完整事实在本地日志中。
4. 当 API Loop 产生修图结果时，系统应该输出 LookLift 结构化候选（参数变更、解释、限制和证据），进入 CandidateRuntime/Verifier；不得使用 OpenDesign 的 HTML artifact 直接改写正式版本。
5. 当 API 请求超时、取消、达到工具轮数上限或上下文预算不足时，系统应该结束当前 Attempt 并保持正式版本不变，不得自动切换 Runtime。

### 需求 9 - 无 CLI 时的 BYOK Harness

**用户故事：** 作为只配置了 API Key 的用户，我希望系统在本机没有任何 CLI 时仍能完成受控的多轮工具调用，并能追踪每一步发生了什么。

1. 当执行选择为 API 且本机 CLI 探测结果为空、不可用或未启用时，Harness 应该直接使用 ProviderConfigStore 中的 API 配置创建 Attempt；不得探测、启动、安装或回退到 Pi、OpenCode、Claude Code 等 CLI。
2. 当 Harness 建立 Provider 请求时，系统应该冻结 `provider_id + base_url + model + config_version`，通过本地 Daemon 发起 Provider-specific SSE 请求；API Key 只从凭据引用解析，不得进入 Run Manifest、普通日志或 SSE 给前端的事件。
3. 当模型返回工具调用时，Harness 应该只允许 LookLift 工具契约中的工具，校验工具名称、JSON Schema、路径范围和参数上限；拒绝结果必须作为结构化工具错误回写模型并记录审计事件。
4. 当工具循环继续执行时，单次 Attempt 的工具轮数应该受固定上限约束；基础 Harness 默认且硬上限为 3 轮（与 OpenDesign `MAX_BYOK_TOOL_LOOPS` 对齐），达到上限、Provider 未返回终态或返回无法解析的事件时，Harness 应该结束为分类失败，不得写入正式版本。
5. 当请求超过超时、用户取消或上游连接断开时，Harness 应该取消上游请求、撤销工具授权并发出唯一终态事件；重复取消不得产生第二个终态。
6. 当上下文超过 token/字符预算时，Harness 应该按“系统契约、照片事实、当前目标、最近工具结果、旧历史”的优先级压缩；压缩后仍超限时，对单条消息和工具结果执行硬截断，并发出包含原始哈希、保留范围和丢弃量的 `ContextCompactionEvent`。
7. 当 Harness 产生 Candidate 时，输出必须符合 LookLift Candidate 协议并经过 CandidateRuntime/Verifier；任何 HTML、SVG、像素文件或未验证参数都只能作为被拒绝的工具结果，不能直接落盘为正式版本。
