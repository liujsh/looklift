# 需求文档

## 简介

建立可安装的 Plugin Host，通过 MCP 动态发现、按需暴露和调用插件工具，以“小红书图文发布”验证完整用户工作流。用户修完图，选中几张图片，说“把这次修的几张图片发到小红书，给我配个文案”，Agent 应找到已安装插件、按插件 Skill 阅读图片并准备文案，在用户确认内容和账号之后执行发布。

状态：实施中，2026-09-12；依据本次用户需求形成。属于跨版本增量，版本归属待收口时确认；不宣称 v2.7 已完成。配套：[技术设计](design.md)、[实施计划](tasks.md)。

完成条件：三份规格的职责、权限、运行终态和发布语义一致，一次一致性检查后停止文档细化。

## 范围与约束

- 首批正式验证小红书图文；抖音是后续适配候选，复用通用宿主。
- LookLift 核心拥有通用安装、连接、发现、预算、素材授权和确认机制；平台 API、页面操作、文案 Skill、工具映射放在插件包。
- 保留 Python 核心、Tauri + React 壳、白盒参数和唯一渲染实现。插件只能接收用户选中的导出成片，不得改变原片或正式参数。
- 外部模型只看最长边 2048px、无 EXIF 的安全预览；明确确认的社媒发布目标可以接收用于发布的导出成片。这是两种不同的数据授权。
- 不开放任意仓库代码一键执行，不开发通用 Shell 工具，不引入无人值守营销、自动评论、批量点赞或爬取图库。
- 实施按任务计划分阶段推进；自动验证只使用本地 Fake 插件，不安装未经审核的第三方程序、不登录、不发帖。Git 写操作仍须用户明确指示。

## 需求 1 — 可插拔与职责分离

**用户故事：** 作为用户，我希望安装插件后即能使用其能力；作为维护者，我希望新增平台无需修改 LookLift 业务代码。

1. 当用户安装兼容插件时，那么系统应读取包内 Manifest、Skill 和 MCP 配置，通过统一宿主登记能力。
2. 如果平台需要特殊参数映射、网页适配、草稿或发布结果解析，那么相关实现应归属插件包，不得写入核心的平台分支。
3. 当增加第二个符合契约的插件时，那么安装、发现、确认与调用流程应复用同一宿主，无需新增平台专属路由或组件。

## 需求 2 — 图片选择与自然语言入口

**用户故事：** 作为摄影用户，我希望用当前选中的成片直接启动配文案和发布。

1. 当用户明确选中照片并提出发布请求时，那么系统应冻结选中集合、正式版本及导出内容身份，生成任务上下文。
2. 如果“这次修的几张”不能唯一对应选中集合，那么系统应让用户选择图片，不得扫描整个图库自行补齐。
3. 如果所选图片只有未确认候选或未完成导出，那么系统应提示完成既有保留/导出步骤；插件不得绕过这些确认。
4. 当 Agent 配文案时，那么它应能读取所选成片的安全视觉预览；如果 Runtime/模型不支持图片，那么系统应说明限制并允许用户补充描述，不得声称已经看图。

## 需求 3 — 意图发现与工具检索

**用户故事：** 作为用户，我希望不用记工具名字，一句话就能找到正确插件。

1. 当任务提及平台或能力时，那么宿主应从本地目录检索插件摘要与工具描述；Agent 应结合目标、选图和检索结果决定下一步。
2. 当检索发生时，那么系统应先按安装、启用、项目、账号与策略范围过滤，再排序；检索不能授予新权限。
3. 如果插件缺失、未登录或权限不足，那么系统应提供对应安装、登录或授权入口；不得自动装包或切换账号。
4. 如果检索无结果或多个候选不能区分，那么系统应支持改写查询、按插件分页浏览或向用户澄清；不得无限检索或静默选错平台。

## 需求 4 — 渐进暴露与上下文预算

**用户故事：** 作为用户，我希望装很多插件后，Agent 仍保持较短上下文和可靠选择。

1. 当宿主获取 MCP 工具目录时，那么完整目录应留在本地，不能默认全部注入模型。
2. 当相关工具集较小且满足预算时，那么系统可以直接加载；如果超出预算，那么应只暴露发现入口，按需加载匹配工具的完整 Schema。
3. 当工具、Skill、Reference 或结果被加载时，那么应计入同一请求预算并记录采用或省略原因；不能截断 Schema 结构来勉强塞入。
4. 当旧工具不再相关时，那么可从后续请求的活动工具集移除；已有调用与结果必须保持配对，不能声称已经消除 CLI 历史中的旧内容。

## 需求 5 — 多 Runtime 兼容

**用户故事：** 作为用户，我希望 CLI 和 API 模式具有相同插件能力与确认边界。

1. 当 API Harness 支持工具调用时，那么宿主应把选定 MCP Schema 转成该 Provider 的工具格式，并将调用路由回统一网关。
2. 当 CLI 支持原生 MCP 时，那么应连接 LookLift 受控代理；如果不支持原生 MCP但支持扩展工具，那么应通过通用桥接调用同一网关。
3. 如果 CLI 不支持动态工具集，那么应使用有界的发现/描述/调用桥接，而不是注入全部插件 Schema。
4. 如果某 Runtime 无法阻止绕过网关或不能保持调用与确认事实，那么应标记插件执行不支持；不得根据名称或 `supports_mcp` 字段推断已兼容。
5. 当执行插件任务时，那么应允许无修图候选的任务终态，不要求为了结束发布任务调用 `finish_candidate`。

## 需求 6 — Skill 与确认边界

**用户故事：** 作为用户，我希望 AI 自主配文案，但真正上传、存平台草稿或发布前可检查内容。

1. 当用户启用相应插件能力时，那么 Agent 应按需读取插件 Skill，了解观察照片、配文案、校验与异常处理流程。
2. 当工具将上传素材或写入外部平台时，那么宿主必须冻结并展示目标账号、内容、图片顺序、接收方、可见性和时间，经用户确认才能执行。
3. 如果 Skill、MCP 输出或模型参数声称“已经批准”，那么不能代替宿主保存的用户确认。
4. 如果确认后的内容、账号、素材、时间或插件版本发生变化，那么旧确认应失效；重新确认后才能执行。
5. 当仅准备本地文案或草稿时，那么不得隐含上传图片；本地草稿、填写平台页面和平台草稿箱应显示为不同能力。

## 需求 7 — 安全与凭据生命周期

**用户故事：** 作为用户，我希望插件只能通过获准操作使用选中素材，且我能停用并清理授权。

1. 当调用插件时，那么服务端应重新校验插件版本、工具身份、Schema、Grant、素材及确认凭证；隐藏工具名不是安全控制。
2. 如果请求包含任意原图路径、Shell、私有网络目标或越权素材，那么应拒绝并记录原因。
3. 当用户撤销时，那么应阻止新调用、失效本地令牌、取消待确认操作，并按连接范围回收会话和进程；已产生的外部副作用不能宣称被撤销。
4. 当使用平台 Cookie 时，那么必须视为敏感会话凭据，不得称为最小作用域 OAuth 或真正的一次性平台授权。
5. 如果缺少操作系统级隔离，那么 UI 和文档应明确“受审查本地程序”信任边界，不得宣传 sidecar 或临时目录等同安全沙箱。

## 需求 8 — 安装目录与版本

**用户故事：** 作为用户，我希望在插件页看到真实可用插件，安装和升级无需手动修改配置。

1. 当用户打开官方精选目录时，那么应看到来自版本化、可校验目录的包元数据，而不是把 GitHub 搜索结果当成可安装插件。
2. 当安装插件时，那么应校验来源、许可证、平台兼容性、包完整性及依赖，并在用户确认后启动程序。
3. 当更新改变工具 Schema、风险或权限时，那么应重新审阅；运行中的 Attempt 固定旧快照，安全撤销优先于版本固定。
4. 当卸载时，那么应停止执行并保留必要历史证据；账号凭据清理应可见且独立于保存历史记录。

## 需求 9 — 发布可靠性与恢复

**用户故事：** 作为用户，我希望网络异常不造成重复发帖，也不把未证实结果显示成成功。

1. 当外部写入超时、断线或进程退出且结果无法确定时，那么状态应为“结果未知”，不得自动重发。
2. 当上游提供可查询回执时，那么系统应据此核实结果；如果没有帖子 ID 或链接，那么不得编造成功链接。
3. 当恢复任务时，那么应恢复草稿、选择、版本与调用事实；不能重放发布副作用或复用过期确认。
4. 当写入已在平台受理后取消时，那么系统应明确取消的是本地等待，不能保证平台内容未发布。

## 需求 10 — 可观测性与验收

**用户故事：** 作为维护者，我希望证明渐进暴露节约上下文且不损害任务完成率。

1. 当任务执行时，那么应记录目录快照、检索、Schema 加载、工具调用、确认及结果摘要，隐藏密钥与原图路径。
2. 当评价方案时，那么应对比全量、任务预选、渐进加载的工具 token、检索命中、参数错误、耗时和任务完成率。
3. 当运行自动测试时，那么应使用 Fake MCP、Fake Harness、临时目录与脱敏素材，不触网、不访问真实账号或 `~/.looklift`。
4. 当记录真实平台验收时，那么应区分文档宣称、源码核对、离线通过和人工实测；安装成功不等于发布可用。
