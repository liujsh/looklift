# 需求文档

## 简介

将 API Harness 与本地 CLI Harness 统一为声明式 Runtime Registry，使新增 Provider/CLI 主要通过注册能力和传输定义完成，不复制生命周期、取消、模型发现和事件归一逻辑。

## 需求

### 需求 1 - Runtime Definition

**用户故事：** 作为开发者，我想通过数据定义接入新的 Harness，以便不修改通用运行引擎。

#### 验收标准

1. 当注册一个 Runtime 时，系统应该要求唯一 ID、显示名称、类型、探测方式、输入方式、流格式和能力声明。
2. 当两个 Runtime 使用相同 ID 时，系统应该在启动时拒绝整个注册表并报告冲突。
3. 当新 Runtime 复用已有流格式时，系统应该无需新增专用事件解析器。

### 需求 2 - 探测与模型发现

**用户故事：** 作为用户，我想看到本机可用的 CLI、认证状态和模型，以便选择可用运行时。

#### 验收标准

1. 当应用检测 Runtime 时，系统应该并行执行可执行文件、版本、能力、认证和模型探测。
2. 当单个 CLI 探测失败时，系统应该隔离该失败并保留其他 Runtime 的结果。
3. 当 Runtime 支持动态模型发现时，系统应该优先展示实时结果，并保留受控静态回退。

### 需求 3 - 统一生命周期

**用户故事：** 作为 Agent Runtime，我想统一处理启动、流式事件、取消、超时和释放，以便 API 与 CLI 具有一致的运行语义。

#### 验收标准

1. 当 Runtime 启动一次 Attempt 时，系统应该产生统一的开始、文本、工具、候选、用量和终态事件。
2. 当用户取消 Run 时，系统应该先撤销权限与 Lease，再按 Runtime 能力执行协作式取消和进程回收。
3. 当事件晚到或序号无效时，系统应该丢弃其业务副作用并记录脱敏错误。

### 需求 4 - 能力门控

**用户故事：** 作为用户，我想知道某个 Harness 支持哪些能力，以便不选择无法完成任务的运行时。

#### 验收标准

1. 当 Runtime 声明不支持图片、MCP、Resume 或结构化事件时，系统应该在 UI 中标记限制。
2. 当任务需要某项未声明能力时，系统应该在启动前阻止运行并说明原因。
3. 当 Runtime 切换时，系统应该创建新的 Attempt，不自动跨 Provider 降级。
